# 可选的选题、写稿与成稿审核协作

用于用户明确采用团队/多 Agent 工作方式时。下列是职责分工，不要求安装固定机器人、建立固定长链或每次启用全部角色。
当前任务、明确指定执行者、独立处理、只要稿或免审核要求优先；不改变与内容工作无关的职责。

## 按任务交接

- 选题提出者：沿用账号资料与真实素材，先公式、稿型和主线，再标题与对应框架。
- 选题审核/写稿者：检查生活理解、代入、账号关联、素材依据和可写性；通过后按要求写，不通过就定向修题。
- 成稿审核者：按 [脚本初审规范](script-review.md) 检查正文，给有依据的少数问题和具体改法；不默默替作者重写。
- 修改者：按 [修改规范](script-revision.md) 判断意见与修法，保留成立的表达，再交当前推荐版。
- 复审者：按 [二次复审规范](script-rereview.md) 核对修复效果、版本收益和旧意见；通过就保留，不增加形式循环。

单个 Agent 可以按当前任务完成相应工作，但角色切换或自查不自动等于独立复审。
用户免审核时不额外跑或输出独立审核流程；仍须遵守真实性、用户约束及必要校对，不能用免审掩盖决定性缺口。

## 成稿审核执行要点

先从全文判断承诺和实际交付，没有全文不能假装审过。叙事查事件、知情、因果与已知结果；解答查答案、条件、数字口径和有依据的做法。
检查当前项目结构是否各有作用、已有标记是否擅删，不追加无用模块。
检查事实与来源、第一次听的主语动作对象、书面套话与重复、用户指定口语和范围、业务边界，以及修改收益。
问题性质分为明确问题、条件风险和可选风格；通常给 1–2 个最重要的实质问题，更多重大问题存在时给足必要信息。
意见交给作者定向修改，不要求照抄审核者措辞；作者其他有效修法应认可。

通过后忠实保留作者推荐正文，标清作者与文本审核者，不借“通过”再次改写。
文案通过不能说成已真人试读、事实全部查证、已发布或业务效果得到验证；缺决定性材料不标为可拍定稿。
真正向外部队列、群、私聊或同事发送，必须有用户授权与实际可用链路；没有发送回执不称已转交，只读环境不称已写入或同步。

## 简洁输出与项目偏好

灵感请求可只展示“内容类型｜标题”，公式与判断内部完成；正式要求公式、评分或筛选时展开对应结果，不以短回复省去必需成果。
原项目的短回复、口语与时长偏好放在 [项目配置](../assets/source-project-profile.md)，不强加到所有账号。
材料足够时内部完成必要检查再交付；用户没要求选题确认时不另增“可以开始写吗”。
